# Separate instrumented Gateway child preparation

This candidate 290 record is preserved. The later source-only native parent wiring and proposed two-child scope are described in [instrumented-gateway-parent-scope.md](instrumented-gateway-parent-scope.md); neither record establishes execution.

This is source preparation, not executed ownership evidence or release acceptance. Production files remain the same 213-file inventory as the unmodified CLI diagnostic at commit `760dba0c7ab9f44b8eb7e00a4b53923272ea488a` (run `41990160342`, job `127120220376`). Those historical raw-CLI results do not qualify this distinct instrumented bundle. No child, build, Inspector session, socket or CI run was started for this revision.

The isolated layout contains `ownership.cjs`, the exact frozen `activate.cjs`, projected `package.json` and `package-lock.json`, and required-only installed dependencies under `node_modules`. Explicit preparation verifies the frozen source bridge and unchanged production inventory, successful bounded compiler acknowledgement, compiler identity, activation bytes, projected manifest and lock. Future native setup must exclusively create this owned layout and install only locked required dependencies with scripts disabled; there is no implicit setup, install or launch in the controller.

Before launch, the controller takes two descriptor-backed full file censuses. Every regular file, including JSON and extensionless files, enters the exact UTF-8 byte map. Symlinks, hardlinks/duplicate file identities, path aliases, writable-by-other ownership, special files, unsupported nested package overrides, undeclared packages, invalid UTF-8 and binaries fail closed. The flat locked package closure must match installed name/version metadata. Limits are 512 files, 4,096 directory entries, depth 32, 32 MiB per file and 64 MiB aggregate; these are acceptance/read bounds, not filesystem quotas. Unexpected package layouts are unsupported rather than excluded from observation. Current Node builtin identities are not authenticated by script replay; the Node executable itself is separately hashed.

Each child receives one exclusively created, bounded canonical input file outside that censused directory: `child-input-compatibility.json` or `child-input-ownership.json`. It contains a fresh nonce, synthetic token and exact copied binding; token and input contents are never emitted. The fixed argv is the admitted canonical Node executable, owned `activate.cjs` and the mode-specific input path. Shell, inherited Node preload/search options, stdin and arbitrary argv are unavailable. The child independently re-reads input, hashes its running Node executable, checks Linux x64 / Node `v24.22.0`, and repeats the complete census before any private Inspector work. This exact version is a proposed prerequisite, not a locally qualified runtime.

The first, separate compatibility mode creates only a private in-process `inspector.Session`. It requires no existing Inspector endpoint, replays compiled scripts and compares canonical file URLs plus exact `Debugger.getScriptSource` strings to prelaunch bytes. It neither starts the Gateway factory nor opens an HTTP listener. A 15-second observation deadline fails; CommonJS wrappers, unexpected anonymous/alias/sourceURL scripts or missing artifact replay are rejected, not normalized or admitted after observation. The exact Node/CommonJS behavior still needs a real compatibility child on the proposed hosted runtime. A failed probe must stop the sequence; changing source normalization would need a separate reviewed change.

Ownership mode requires an unconsumed in-memory capability returned by the actual parent-observed compatibility child. Serialized receipts and synthetic claims do not grant it. The binding, census identities and Node identity must still match. Distinct exclusive input paths allow the two children without deleting or overwriting the first input. One capability admits at most one ownership attempt. This mode runs the existing 45-second instrumented workload: one IPv4 loopback health request, actual product close, zero sampled product counters, and private Inspector disable/disconnect acknowledgement. Active HTTP client closure does not imply server retirement; only product close joins the product counters.

A ref'ed child liveness interval remains until known workload retirement and stdout write callback acknowledgement. Rejected results alone do not retire those resources. Unknown acquisition/dispatch/cleanup outcomes stay held and are never retried. An error observer is attached before stdout write and retained for the child's lifetime, including callback-error/event ordering and late errors; late error sets exit status to failure. The callback retires the write, not the inherited pipe or error observer. The parent requires actual exit 0 with no signal and child/stdout/stderr close observations before accepting the single canonical nonce-bound receipt, then repeats all file, Node and input checks. Stdout is capped at 32 KiB, stderr at 64 KiB, 1,024 chunks each, with a 60-second direct-child observation deadline. No signal, force exit, deletion, automatic retry, global stdout close or external debug endpoint is exposed.

The native activation entry is inert until explicitly called by the fixed CJS activation. The parent controller has explicit filesystem, exclusive-write, child-launch and timer ports; a real hosted driver wiring those ports is not supplied or executed by this revision. Unsupported filesystem/port returns and errors fail with retained custody. A directory census cannot protect against malicious same-user/admin mutation between observations; the selected staging parent and runtime environment must be trusted. No shipping debug surface is added.

A concrete future execution proposal is one standard public Ubuntu job, at most 20 minutes, official locked dependency downloads, no artifact/cache upload and a sanitized receipt at most 16 KiB. It would need to explicitly authorize **two sequential children**: the compatibility child first, then one ownership child only if the actual capability is obtained. That differs from an earlier one-child idea and is not implicitly executed by this source-preparation task. Each child/pipe closure remains distinct from whole-process-group retirement. On timeout, cancellation or uncertain child custody the job stops; any disposable runner teardown requires its own approved diagnostic scope and proves no graceful descendant retirement. Existing $0, package/storage, native/DUT and release holds remain unchanged. No real application performance, soak, GC, raw-CLI behavior or release qualification transfers from these synthetic checks or from the instrumented build.
